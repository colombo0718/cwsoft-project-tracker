# 2026-05-21 cwsoft 客服

## 今日處理案件

### 1. 速利通訊 — POS 跳「呼叫主程式找不到檔案」

客戶反映打開 POS 跳這個視窗。第一版回覆我提了「先檢查資料夾 → 看防毒隔離區 → 重跑說明.exe」這條路線，被 colombo 用同事既有 SOP 修正：

**同事提示更實務的順序：**
1. 桌面捷徑右鍵 → **以系統管理員身份執行**
2. 不行再去執行 `說明.exe` 點「最新版本」重新更新

理由：POS 裝在 `Program Files (x86)` 底下，UAC 阻擋時很容易跳出「找不到檔案」這種誤導訊息。試 admin 比翻防毒隔離區便宜很多。

學到：硬體/環境問題的排查順序是「**先試最便宜的、最常見的**」，再走深技術線。

### 2. 馬尼 — 庫存查詢表匯 Excel 完全沒反應（主案）

客戶在「庫存查詢表」（結帳報表 → 庫存查詢表）篩玻璃貼後按匯Excel + 「是」，畫面完全沒反應。深度追查全程在 [2026-05-21-cwsoft-mani-excel-export-bug-and-linebot-coupon-data.md](2026-05-21-cwsoft-mani-excel-export-bug-and-linebot-coupon-data.md)。

**簡要結論：**

LINE bot 把 87 字優惠券領取記錄（`linebot/{bot}/users/U.../coupons/...`）塞進「商品資料」欄，但 POS 客戶端 XSD 把這欄寫死成 50 字，匯出時 `DataTable.Copy()` 觸發 MaxLength 檢查炸掉，但 Catch 吞掉錯誤 → 看起來像沒反應。

**追查里程碑：**

1. 先誤判為「timeout 被吃掉」——被 colombo 「反芻驗證」打回，承認過度斷言
2. 在 VS 復現，改 Catch 為 MsgBox 才抓到真正錯誤：MaxLength 違反
3. 比對 `ds庫存查詢表.xsd`（maxLength=50） vs DB schema（nvarchar 150） vs 實際資料（87 字）→ 鎖定 XSD
4. 列出馬尼東門店所有超長記錄 → 64 筆全是 LINE bot 格式
5. 確認商品分類 → 4 個優惠券 + 1 個玻璃貼 + 1 個手機（複製貼上失誤）
6. 比對時間軸 → 2024/9 LINE bot 系統升級把格式從 20 字 coupon ID 改成 87 字完整 URL，從那時起埋雷

**處理結論：**

我一度想「直接幫客戶用 DB 撈成 Excel」，被 colombo 打回「那下次他要新表是不是又找你撈？這條路走不下去」。後來想「請客戶自己改超長資料」，又發現是 LINE bot 系統自動寫入的不是客戶填的，叫客戶清不合理。

最終策略是把問題丟給同事/老闆討論（A 截斷 / B 改 XSD / C 改 SP 三條路），由他們決定。**寄給客戶的訊息採「問客戶有沒有這方面使用需求」的試探式包裝**，沒直接承認是 LINE bot 系統的 bug，保留主動權。

## 客服技巧

### 反芻驗證救了我一次

太早跳「2024 年舊系統 trigger bug」「按是沒反應 = timeout」這種結論。colombo 兩次提醒「反芻驗證一下」才把我拉回——沒實證的話只能說「最可能」不能說「就是」。森昱那案也一樣，最後改成「無法溯源」的誠實版本。

### 不要替客戶代勞做表

第二次踩這個坑了。客戶卡 UI 我想救火直接撈 DB → 被打回「下次新條件還要你做」。**正確做法是修程式 / 修 SP，讓客戶端能自助**。

### 客戶訊息策略：先試探需求，再決定要不要承認 bug

當問題是「**我們系統 A 寫進去的東西打到系統 B**」這種內部矛盾時，先問客戶有沒有這方面需求，得到答案再決定走「治本修 A」「治本修 B」「直接清資料」哪條路。不要急著對客戶說「對不起我們有 bug」。
