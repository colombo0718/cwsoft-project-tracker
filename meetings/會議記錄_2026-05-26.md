### 主題2｜MCP 安全性 / 外部呼叫風險 / 二次驗證
- 老闆問：「外部的 AI 有辦法去呼叫這個 MCP 嗎？」
- 士豪：MCP 像「AI 版的 web service」、即便是 Python 腳本也能呼叫
- 對齊策略：
  - 既有 API（sgateway 等）有認證、知道呼叫者身份
  - MCP 目前的權限**是放在阿全這層**判斷「你是誰」
  - 風險：外部 AI 可能繞過阿全直接打 MCP 不夠安全
- 解法：**MCP 設成 private、只能我們自己呼叫**
  - 「全縣城」(指阿全)只放這個權限檢查，外部一概不行
  - 把 MCP bundle 在一起、不繞過權限檢查、避免類似資料庫 login 沒有就不行的同等保護

### 主題3｜特殊權限的獨立 app（高級版阿全、指紋認證）
- 觸發：例如「改員工 1001 的密碼」這種敏感寫入動作、不能直接給阿全做
- 設計：
  - 寫**一隻獨立 app**（iOS / Android）作為「高級版阿全」
  - 啟動時用**手機指紋認證**（類似 Google Authenticator / 銀行 OTP 二次驗證）
  - 認證後才開啟更多權限
  - 跟阿全是**兩個介面**：阿全處理日常、特殊權限 app 處理需身分驗證的寫入
- 實作 channel：
  - 阿全判斷不能執行 → 把任務丟進 DB → 獨立 app 開啟時去 DB 拉「待認證」項目
  - 指紋認證通過後執行
  - 完成後回寫 DB → 阿全告知 user「已完成」
- 認證機制取捨：每次重新認證 vs 認證一次後續都通 → 老闆傾向**每次都認證**比較安全
- 老闆比喻：類似中國信託 LINE + app 雙介面架構

### 主題4｜基本資料統一控制 MCP（動態抓開關清單）
- 老闆 wishlist 累積：
  - 開啟法博維修站系統
  - 成峰總倉銷售要關閉
  - 前進的自訂成本要打開
  - 在途庫存系統
  - 簡訊點數（已做）
- 觀察：這些**全在客戶 DB 的 `dbo.基本設定` 表**（key-value 結構）
- 例外：**手機版設定在「行動裝置設定」表、不在基本設定**
- 解法：寫**一個通用 MCP**
  - 先**動態抓**客戶 DB 的 `dbo.基本設定` 列出有哪些開關（不寫死 list）
  - 再依 user input 調整對應 row
  - 一個 MCP 解掉這類「修改基本設定 row」的全部 wish
- 進階性：比單一 toggle 困難一些，因為要先 schema introspection

### 主題7｜通知訊息重要 vs 一般 + 時段設定
- 觸發：阿全半夜會推送「我學會什麼新功能」之類非緊急訊息、老闆覺得太擾人
- 設計：
  - 訊息**分等級**：重要（緊急）vs 一般
  - 緊急（例：帳款狀況）→ 馬上推
  - 一般（例：新功能 / 學習進度）→ 等使用者設定的時段才推
  - **每個 user 自己設**接收時段（例：9 點到 9 點 / 上班時間）
- 老闆例：「晚上 10 點之後我實在不太想說這個」、「想要打電動就打電動、不用理他」
- 未來：阿全可以**綁老闆家進 3 人家庭群組**、不用 LINE OA

### 主題12｜標籤機尺寸：基本設定 vs 單機設定
- 馬尼反映：列印型號 / 列印序號的設定 boss、改自訂後後面設定還是讀基本設定的值

### 主題14｜AI 應用四層架構歸納（士豪 retrospective）
歸納近期用 AI 的層級：

| 層 | 工具 | 場景 | 成本 |
|---|---|---|---|
| 1. 透徨 / 拓荒 | Claude / Codex CLI 最新模型 | 完全不知道怎麼處理的問題 | 最貴、需要最聰明模型 |
| 2. MCP 封裝 | 把處理好的事情包成 MCP | 知道怎麼處理、要重複用 | — |
| 3. 二三線 agent | gemini-cli 等較弱的 coding agent + MCP | 已有 MCP、agent 只負責調用 | 便宜 |
| 4. 純腳本 | 本地 LLM + 完全 script 化 | 完全打通的問題、不需 AI | 最便宜、最快 |

- 老闆：「一開始最上面那層要花最多錢用最新模型、拆完之後用比較舊模型」
- AI 智能進步超快、Codex CLI 兩三週就大幅進步
