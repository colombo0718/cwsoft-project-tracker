## 3) 討論摘要

### 主題1｜零壹通訊行 Message API Channel 控制權危機

- **現況**：零壹的 LINE 官方帳號 Message API Channel **控制權目前在第三方廠商手上**、不在零壹自己也不在 cwsoft。零壹老闆已知道狀況、跟原廠商交涉中、但拿回希望不大（「廠商拿走這個可能就不太可能會回來」）
- **彥偉要求羿宏寫一份 PPT**：給零壹老闆談判用、內容不用多、就是把「拿不到 channel API 的解法」講清楚
- **三種解法路徑**：
  1. **拿回控制權**（最理想、機率低）
  2. **建新官方帳號 + 舊會員遷移**（cwsoft 主推、配套行銷活動）
  3. **跟廠商要回**（最後手段）
- **遷移誘因設計**：滿千送百、續約折 100 元、或某種折價券——「讓人家心甘情願轉過來、客戶也能順勢做行銷活動、雙贏」
- **自我檢測流程**：羿宏設計一段流程讓零壹自己確認——「進去之後看到什麼就代表什麼」、看 message API 設定裡的選項判斷 channel 有沒有被其他廠商申請過
- **零壹有 4 個官方帳號要處理**——彥偉強烈建議全部整成 1 個，「特別麻煩、而且那 4 個全部都是...」

### 主題2｜OK App 競爭策略

- **OK 商業模式**：把所有客戶會員折價券抓到自己 app 裡、每個使用者都要下載 OK 會員；定期發折價券
- **OK 為什麼搶 Message API**：怕被換掉。會員資料雖然 cwsoft 也有一份、但 channel API 被 OK 拿走就難整合
- **彥偉的競爭分析**：「OK 把 API 據為己有對他來講利益最大化、但對客戶不利。我的想法是：你不用我服務時我就還你 channel API、但你不用我我也不繼續串 LINE 按鈕跟 AI 智能功能」
- **三軌策略**：
  1. **搶**：把 OK 的 channel 搶過來
  2. **同步**：跟 OK 同步點數（OK 有跨異業點數 API、布魯斯案例：可換按摩店點數、餐廳點數）
  3. **大量布點**：channel ID 先搶先贏的情況下、大量布點同時拿到營收 + 卡位
- **競爭關鍵句**：「我的功能跟 POS 整合、人家比較換不掉。OK 只有做會員功能、我們同步進行一段時間之後、客戶會覺得 OK 多餘、就會先取消比較貴的那個」
- **法律配套**：「合約上很明確講你不使用我就還你」——彥偉提到有律師服務、要看內容能不能用

### 主題3｜公司用客服 OA 帳號 + 個人 LINE 清理 + 舊客服遷移

- **痛點**：
  - 全國觀光客服部的綁定**綁在老闆手機**上、每次調整客戶圖文選單都要老闆輸入驗證碼、超麻煩
  - 業務跟客服都用彥偉個人 LINE 帳號、混在一起、半夜會被吵
- **規劃**：
  - **建一個公司用客服 OA**（名字暫定「客服資訊」或「工程」）、之後加入客戶的官方帳號時用這個身份、不用每次跟老闆要驗證碼
  - 把彥偉個人 LINE 的「**試用**」「**小助手**」官方帳號授權**先拿掉**（請士豪幫忙）；個人帳號保留 GB 那個（業務聯絡用）
- **舊客服→新 OA 遷移**：
  - 還有「**誠信 / 誠哲**」等少數客戶用舊個人帳號聯絡彥偉
  - 彥偉自己把這些慢慢移到客服官方帳號
  - 委婉跟客戶說：「現在有客服部、白天回」——半夜訊息就拖到白天
- **彥偉的對客原則**：「業務的事我用個人、客服的事走客服部、區分很開」

### 主題4｜阿全經理 codex 版展示與設計討論（士豪報告）

- **架構講解**（士豪）：
  - 入口跟原本 GTP 一樣
  - 底層直接接 codex
  - **擋掉 codex 自己會跑的寫操作**
  - 開放讀的部分：用 MCP 開個別檔案、kb 知識庫等
  - 「讀的部分開得很 open、寫的部分比較保守一點」
- **MCP 標記系統**（士豪展示給彥偉看）：codex 對話中會自己標 4 種 tag、後台 grep
  - `[KB_FIX]` 對 cwsoft 知識理解錯被糾正
  - `[WANT_NEW_TOOL]` 使用者要某功能、沒對應 tool
  - `[BUG_SIGHTED]` 發現怪事
  - `[ACTION]` 真執行了寫入操作
  - 寫進 `notebooks/notebook_YYYYMMDD.md`、彥偉/colombo 可看
- **彥偉提：訊息單位 vs 對話單位**：
  - 影子模式以單一訊息為單位、回應不連貫
  - 士豪：codex 是看上下文的、已經能跨訊息串連
  - 但「**多人對話會混茶**」——同時多人講話會錯亂（彥偉 + 宜龍同時對阿全講「加幾點」跟「好」）
  - 解法：拆 SID（per-user session）、每人一條獨立對話 → **士豪後續工作**
- **點數類型區分需求**（彥偉提）：
  - 一般點數 vs **簡訊點數** 要分開
  - 例：「誰誰加六點」要能判斷是哪種點數、或自動釐清「您講的是簡訊還是月初點數?」

### 主題5｜AI 客服信心度策略（**核心爭論**）

- **彥偉的堅持**：
  - 年底要 **10% AI 自動回答**、明年 50-80%
  - 但**信心度不夠就不要送出**、由人監督
  - 「我不會去讓客戶得到一個他覺得不行的答案。即便是 AI、也要『行』的才回」
  - 「**不要讓客戶感覺是 AI 回答**」——分不出來、覺得服務有水準
- **羿宏不同看法**：
  - 「銀行的 AI 客服其實也沒有...他們做這個主要是為了**收集數據**」
  - 「客戶角度去用銀行 AI 時、本來就不會對答案有期待」
  - 客服忙不過來的時候、用 AI 讓客戶不用等
- **彥偉反駁**：
  - 銀行那種策略是高層做的、「**上層完全不知道 AI 回答的準確度是多少**」
  - 「太多例子是把客服全換 AI、結果回答亂七八糟把客戶得罪光、再回來」
  - 「我看完之後覺得這還不到可以直接送的程度、那我寧可一開始多用一點能力」
- **變通方案**：
  - 「**我們了解問題、晚一點回你**」——這句不算敷衍、客戶能接受
  - 訊息群組裡「非上班時間」自動回會誤觸（首例案例：丟帳單收到非上班時間回覆很尷尬）
  - 進階聊天訂閱 1000+/月、暫時不買、需要時再買
- **羿宏方案被否決**：「老闆的 LINE 行動裡有兩種模式、一種是客服、另一種是 AI 回答、讓客戶選」→ 彥偉：**不要、要讓客戶分不出來是 AI**

### 主題6｜零壹上線測試流程與宇新 6 月初 demo

- **零壹**：
  - 點數兌換已驗證可行（已收錢）
  - 內部測試→ 請零壹幫忙複測 → 開放
  - 改點數中間時間（中間點數要補）
  - LINE 圖文選單已綁定、下午測試完即可開放、3 天試用
- **宇新**（6 月初）：
  - **羿宏做一份 demo**（不用多頁）
  - 讓老闆能直接用手機點 LINE 圖文選單體驗
  - 後面再串實際功能

### 主題7｜綠界金流串接 + 1/6 個月繳費合約

- **彥偉要 ai 串金流**：
  - 之前看到一個叫 **Globo** 的全球都能用、但這次選 **綠界**（藍星不行）
  - 想要：收款後自動知道、自動幫客戶加點
  - 綠界本身有金流 + 電子發票
- **缺**：綠界帳號密碼彥偉沒給過士豪、要找會計拿
- **繳費模式新增**：
  - 新客戶選擇 **1 個月繳 / 6 個月繳**（皆含稅）
  - 不在這兩種以內 → 走電子服務模式
- **使用合約**：彥偉要找律師服務、做一份合約樣板（明確寫「你不使用我就還你 channel API」）

### 主題8｜商品明細列印補強（BC 發票）

- 目前只有 **B（公司戶、有統編）** 的發票會列印商品明細
- **BC（個人戶 + 公司戶）都該有**——彥偉：「我覺得所有發票都應該要有這部分、像家樂福那樣」
- 法規應沒禁止；當初是時間不夠才省略
- 「你買什麼東西、我本來就應該給你」

## 4) 決議
- **零壹 PPT**：羿宏寫、內容含三種解法 + 自我檢測流程；速度、客戶已付錢、彥偉要拿著去談
- **OK 對策**：搶（拿 channel）、同步（OK 點數異業整合）、大量布點 三軌並行；合約寫清「不用就還」
- **公司用客服 OA**：建一個專門帳號（暫名「客服資訊」或「工程」）；個人 LINE 清掉「試用 / 小助手」綁定（士豪幫忙）
- **舊客服遷移**：彥偉自己把誠信 / 誠哲等少數客戶慢慢移到客服 OA
- **阿全 per-user session**：士豪做 SID 拆分、避免多人對話混茶（接 5/16 已規劃方向）
- **點數類型區分**：阿全要會判斷 / 釐清一般點數 vs 簡訊點數
- **AI 客服回應**：**信心度不夠不送、人監督模式繼續**；不讓客戶感覺到 AI；用「了解一下問題、晚一點回你」作緩衝
- **零壹 LINE 圖文選單**：下午測試完即可開放、3 天試用、之後補點數
- **宇新 demo**：羿宏 6 月初做完、含 LINE 手機端體驗
- **綠界金流串接**：開做、要 1/6 月繳費模式
- **商品明細列印**：BC 發票補上去
